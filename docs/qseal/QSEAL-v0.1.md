# Q-SEAL v0.1

## Quantum-Safe Secure Element Attestation Layer

Design specification, v0.1. Q-SEAL is the applied motivation for this project: the ML-DSA-44 primitive it
mandates is what PQC-Assay machine-checks. Protocol-level verification of the properties in section 16
lives in [`../../qseal/`](../../qseal/); the first (TBS-V1 transcript bijectivity) is proved there.

### 1. Purpose

Q-SEAL provides a hybrid cryptographic attestation generated by a non-exportable key held inside an eUICC or subscriber secure element.

It is intended for:

* high-assurance enrollment
* subscription and profile lifecycle evidence
* regulated device or subscriber credential binding
* issuance and rotation of long-lived network credentials
* proof that a specific secure element authorized a defined operation

Q-SEAL does **not** claim that:

* the user personally approved an action
* the handset OS is uncompromised
* the eSIM has independently inspected an arbitrary large payload
* possession of an eSIM key alone proves a legal identity

Those are separate claims that require additional evidence.

---

## 2. Security Claim

A valid Q-SEAL assertion means:

> A non-exportable hybrid attestation key, held by an authorized secure element, signed a canonical statement containing a verifier challenge, intended audience, operation type, expiry, and optional digest-bound object reference.

A valid assertion proves four things:

1. The private attestation keys were available inside the secure element at signing time.
2. Both signatures covered exactly the same canonical transcript.
3. The assertion was bound to a named verifier, operation, and server challenge.
4. The assertion cannot be replayed successfully after the verifier consumes the challenge.

It does **not** prove the integrity of the phone. For that, the verifier must combine Q-SEAL evidence with OEM or TEE device-attestation evidence over the same challenge.

---

## 3. Assurance Levels

| Level | Claim                                 | Evidence Required                        |
| ----- | ------------------------------------- | ---------------------------------------- |
| L1    | Secure-element key possession         | Valid hybrid signature                   |
| L2    | Recognised eUICC provenance           | Vendor or issuer attestation certificate |
| L3    | Active subscriber/profile association | MNO subscription-binding statement       |
| L4    | Device-bound assurance                | Q-SEAL plus OEM/TEE attestation          |
| L5    | Regulated identity binding            | L3/L4 plus identity-provider assertion   |

A relying party MUST only claim the strongest level for which all required evidence has been verified.

A valid L1 assertion is not automatically subscriber identity, device integrity, or KYC.

## 4. Cryptographic Suite

### Mandatory suite: `HYB-1`

```text
Classical signature: ECDSA P-256 with SHA-256
Post-quantum signature: ML-DSA-44
Payload digest: SHA-256
Transcript context: "Q-SEAL/v1"
```

The applet MUST generate separate key pairs for the classical and PQC algorithms.

The verifier MUST require both signatures to validate.

```text
accept(assertion) =
    verify_ecdsa(classical_public_key, TBS, sig_classical)
AND verify_mldsa(pqc_public_key, TBS, sig_pqc)
AND verify_policy(TBS)
AND consume_challenge_once(challenge_key(TBS))
```

The challenge key is the concatenation

```text
challenge_key(TBS) = TBS.verifier_id || TBS.request_id || TBS.nonce
```

A `request_id` is unique per verifier (section 10), so this key is per-verifier and covers the request
identifier and the nonce together. `consume_challenge_once` records the key on acceptance and rejects any
later assertion carrying the same key.

The verifier MUST reject:

* an assertion with only one valid signature
* an assertion where the signatures cover different transcripts
* an unsupported suite identifier
* a request whose challenge key (`verifier_id || request_id || nonce`) has already been consumed
* a signature generated under a legacy-only suite when `HYB-1` was required

There is no "either signature is fine" fallback inside `HYB-1`. That would turn hybrid security into decorative garnish.

## 5. Trust Model

Q-SEAL has three separate trust chains.

```text
eUICC / Secure Element Trust
    eUICC vendor or operator root
        Attestation-key certificate
            hybrid key pair inside secure element

Subscriber Trust
    MNO or subscription authority
        subscription-binding statement
            pseudonymous subscriber / profile reference

Device Trust
    OEM or TEE root
        device-attestation certificate
            handset integrity evidence
```

The verifier MAY combine these chains, but MUST verify each independently.

Q-SEAL MUST NOT replace existing GSMA Remote SIM Provisioning trust chains. It is an overlay attestation layer that can reference profile state or provisioning events without replacing profile-management authorisation.

## 6. Attestation Key Lifecycle

### 6.1 Key generation

The applet MUST generate both keys internally.

```text
AK_classical = ECDSA-P256 key pair
AK_pqc       = ML-DSA-44 key pair
AK_ID        = random 128-bit identifier
```

Private keys MUST:

* remain non-exportable
* be inaccessible to the handset application processor
* be inaccessible to profile applications
* be deleted or permanently disabled on revocation or secure-element retirement
* be single-purpose: both keys sign Q-SEAL canonical transcripts and nothing else. The applet
  MUST NOT expose any other signing interface over either key, and neither key may be certified
  for or used by any other protocol. This matters most for `AK_classical`: ECDSA has no context
  parameter, so key dedication is its only domain separation (from public review follow-up,
  2026-07-13; the ML-DSA context rule is in 7.1).

### 6.2 Certification

The attestation public keys are certified as a pair.

```text
AttestationKeyCertificate = {
    version,
    ak_id,
    classical_public_key,
    pqc_public_key,
    suite_id,
    applet_id,
    issuer_id,
    device_handle,
    not_before,
    not_after,
    policy_id
}
```

`device_handle` MUST be an opaque pseudonymous identifier. Raw EID, ICCID, IMSI, or subscriber identifiers MUST NOT appear in ordinary relying-party evidence.

### 6.3 Rotation

The platform MUST support:

* scheduled key rotation
* emergency revocation
* issuer-root rotation
* algorithm-suite rotation
* migration from `HYB-1` to future suites

A verifier MUST resolve the certificate chain using `ak_id`; the applet SHOULD NOT return a full certificate chain with every attestation response.

## 7. Canonical Attestation Transcript

The applet signs a fixed binary transcript, not arbitrary host-provided bytes.

```text
TBS-V1 =
    magic                   : 5 bytes = "QSEAL"
    version                 : 1 byte
    suite_id                : 2 bytes
    assertion_type          : 1 byte
    assertion_origin        : 1 byte
    issuer_id               : 16 bytes
    verifier_id             : 16 bytes
    ak_id                   : 16 bytes
    request_id              : 16 bytes
    nonce                   : 32 bytes
    policy_id               : 4 bytes
    issued_at               : 8 bytes
    expires_at              : 8 bytes
    subject_ref             : 32 bytes
    object_hash_algorithm   : 1 byte
    object_length           : 8 bytes
    object_digest           : 32 bytes
    associated_claim_digest : 32 bytes
```

All integers MUST be unsigned big-endian values.

The transcript is fixed-length and MUST contain no optional fields, variable encodings, or application-defined byte blobs.

This is deliberate. Canonicalisation bugs are the cryptographic equivalent of leaving a side door open because the main gate had a nice lock.

### 7.1 TBS-V2 (v0.2 draft): hybrid pair binding

Motivation, from public review of v0.1 (r/crypto, 2026-07-12): in TBS-V1 each component signature
commits to the hybrid pair only through `ak_id`, an identifier bound to the two public keys at the
certificate layer. Nothing inside the signed bytes commits to the key material of the OTHER half
of the pair, and FIPS 204's `ctx` parameter is unused. That leaves pair binding resting entirely
on certification, the known non-separability concern for hybrid signatures.

TBS-V2 is TBS-V1 with one field inserted directly after `ak_id`:

```text
    pair_commitment         : 32 bytes
```

Total 263 bytes; `version` = 2. The commitment is:

```text
    pair_commitment = SHA-256("QSEAL-PAIR-HYB1" || AK_classical_compressed_33 || AK_pqc_encoded_1312)
```

the untruncated form of the domain-separated pair hash Cap-V1 uses for its key ids (both inputs
fixed length, so the concatenation is unambiguous without length prefixes).

Rules:

- The applet MUST compute `pair_commitment` from its own key material; a host-supplied value MUST
  be rejected (same applet-controls-identity rule as `issuer_id`/`ak_id`).
- The verifier MUST recompute the commitment from the two public keys it validated via `ak_id`'s
  certificate chain and reject on mismatch.
- The ML-DSA-44 signature MUST be produced and verified with the FIPS 204 context string
  `ctx = "Q-SEAL/v2"`, and that context value is RESERVED in both directions: `AK_pqc` MUST NOT
  produce a signature under any other `ctx`, and no other code path, key, or protocol may sign
  under `ctx = "Q-SEAL/v2"`. A context string only separates domains if it is exclusive (public
  review follow-up, 2026-07-13).
- ECDSA has no context parameter, so message content cannot substitute for domain separation:
  `AK_classical` MUST be a dedicated key per the single-purpose rule in 6.1 (generated for
  Q-SEAL, certified for nothing else, signs only serialized Q-SEAL transcripts). The
  `pair_commitment` identifies the pair inside the signed bytes; it does not protect a key that
  also signs other protocols' messages.
- V1 and V2 cannot be confused on the wire: both are fixed-length with no optional fields and
  231 != 263, so no byte string parses as both.

With this, each component signature commits to the exact hybrid pair rather than to its name, so
a peeled-off component signature identifies itself as half of a Q-SEAL pair. What v0.2 does NOT
claim: any guarantee about foreign verifiers that ignore the transcript format entirely; the
commitment's strength is SHA-256 collision resistance (out of scope of the format proofs).

Machine-checked (qseal/model/QSEAL_TBS_V2.cry, `make qseal-tbs`): the V2 serializer is a bijection
and injective; `pair_commitment` is signed and position-pinned (two transcripts differing only in
the commitment never share bytes); and a serializer that omitted the commitment is witnessed to
collide them (mutation-style non-vacuity). The C reference (de)serializer `qseal/ref/tbs_v2.c` is
proven equal to the model by SAW (`qseal/proof/tbs_v2.saw`, `make qseal-ref`), and the demo signs
TBS-V2 with `ctx = "Q-SEAL/v2"` and performs the verifier-side recompute-and-compare (scenario 7:
a zeroed commitment is rejected with both signatures still valid; an empty-ctx ML-DSA signature
does not verify under the reserved ctx). The key-usage rules (reserved `ctx`, dedicated classical
key) are policy obligations on the applet and its certification, not properties of the transcript
format; on the reference-code side the corresponding checkable statement is that the validated
create path is the only signing call site, which remains open, as does the V2 validate/create
path in the verified C.

## 8. Assertion Types

```text
0x01  ENROLLMENT
0x02  CREDENTIAL_ROTATION
0x03  PROFILE_ACTION_REQUESTED
0x04  PROFILE_ACTION_OBSERVED
0x05  REGULATED_DEVICE_IDENTITY
0x06  NETWORK_CREDENTIAL_BINDING
```

### 8.1 `ENROLLMENT`

Used when enrolling the secure element with a relying party.

```text
subject_ref             = pseudonymous subscriber or device reference
object_digest           = hash of enrollment request
associated_claim_digest = hash of requested service policy
```

### 8.2 `NETWORK_CREDENTIAL_BINDING`

Used to bind a new public key, CSR, or credential request to the secure element.

```text
object_digest = SHA-256(candidate_public_key || credential_policy)
```

The relying party SHOULD issue a short-lived operational credential after successful verification.

The ML-DSA signature is primarily used for enrollment and credential rotation, not for every network packet.

### 8.3 `PROFILE_ACTION_REQUESTED`

Used to attest that a profile operation was requested.

Examples:

* enable profile
* disable profile
* download profile
* delete profile
* transfer subscription

This proves only that the secure element signed a request-bound statement.

It MUST NOT be described as proof that the action completed.

### 8.4 `PROFILE_ACTION_OBSERVED`

Used only when the assertion is generated from a trusted internal eUICC event callback after the profile state transition has completed.

This assertion MUST NOT be callable directly by a handset application.

If the eUICC platform cannot provide a trusted post-operation callback, this assertion type MUST be disabled.

---

## 9. Assertion Origins

```text
0x01  HOST_ASSERTED
0x02  EUICC_OBSERVED
0x03  TEE_BOUND
```

`HOST_ASSERTED` means the host supplied the object digest. The eSIM proves it signed that digest, not that it received or inspected the original payload.

`EUICC_OBSERVED` means the claim was generated by a trusted eUICC service after observing on-card state.

`TEE_BOUND` means the request was additionally bound to a verified OEM or TEE attestation session.

A verifier MUST treat these as different assurance classes.

---

## 10. Server Challenge

The relying party creates the challenge.

```text
Challenge = {
    suite_id,
    verifier_id,
    request_id,
    nonce,
    assertion_type,
    policy_id,
    issued_at,
    expires_at,
    object_digest,
    associated_claim_digest
}
```

Requirements:

* `nonce` MUST contain at least 256 bits of unpredictable randomness.
* `request_id` MUST be unique for the verifier.
* the verifier MUST retain challenge state until expiry.
* a challenge MUST be accepted at most once.
* expiry MUST be enforced by the verifier.
* the applet MAY sign an expired challenge if it lacks a trusted clock, but the verifier MUST reject it.

For high-assurance deployments, the challenge SHOULD include an authorization token signed by a verifier key registered with the applet or issuer security domain.

## 11. Applet Interface

### 11.1 `GET_CAPABILITIES`

Returns:

```text
applet_version
supported_suites
max_assertion_size
supported_assertion_types
supported_origins
attestation_key_status
certificate_reference
```

### 11.2 `CREATE_ASSERTION`

Input:

```text
suite_id
assertion_type
assertion_origin
request_id
nonce
verifier_id
policy_id
expiry
subject_ref
object_length
object_digest
associated_claim_digest
```

The applet MUST:

1. Validate all field lengths.
2. Validate the requested suite and assertion type.
3. Reject unsupported assertion origins.
4. Construct `TBS-V1` internally.
5. Generate both signatures over the same `TBS-V1`.
6. Return an evidence handle or begin response chaining.

The handset MUST NOT supply an already-encoded transcript.

### 11.3 `READ_EVIDENCE`

Returns response fragments for:

```text
Evidence = {
    ak_id,
    suite_id,
    tbs,
    sig_classical,
    sig_pqc,
    certificate_reference,
    applet_version
}
```

The applet MAY retain evidence only in volatile memory.

A reset, APDU failure, or timeout MAY invalidate the evidence handle. Retrying the same challenge may generate a different signature, but the verifier MUST still consume the challenge once.

---

## 12. Access Control

The applet MUST only be reachable through an authorised secure-element access path.

The deployment MUST define:

* which device applications may open the applet channel
* which application signing certificates are authorised
* which assertion types each application may request
* whether profile lifecycle assertions require internal eUICC invocation
* whether verifier authorization tokens are mandatory

A generic handset application MUST NOT receive unrestricted access to a `sign(bytes[])` operation.

There is intentionally no such API.

---

## 13. Privacy Rules

Q-SEAL evidence MUST NOT disclose raw:

* IMSI
* ICCID
* EID
* MSISDN
* subscriber legal name
* profile contents
* device serial number

Instead, the issuer SHOULD provide scoped pseudonymous references.

A different `subject_ref` SHOULD be used per relying-party trust domain unless correlation is explicitly required and legally authorised.

---

## 14. Device Integrity Composition

For strong device attestation, the verifier requests two assertions over the same `request_id` and `nonce`.

```text
OEM / TEE:
    attests device state, boot integrity, application identity

eSIM / Q-SEAL:
    attests secure-element key possession and subscriber binding

Verifier:
    checks same nonce
    checks same verifier_id
    checks same policy_id
    checks registered relationship between device and eSIM
```

The combined assertion means:

> This recognised secure element and this attested device jointly participated in the same verifier challenge.

That is the point at which "device attestation rooted in the subscriber secure element" becomes an accurate phrase.

---

## 15. Threat Model

Q-SEAL is designed to mitigate:

* replay of old enrollment or credential requests
* host mutation of verifier, nonce, policy, or object digest after signing
* extraction of attestation private keys from the handset OS
* compromise of one signature family during hybrid migration
* accidental cross-service use of evidence
* ambiguous or non-canonical transcript encoding

Q-SEAL does not mitigate:

* compromise of the eUICC operating system
* compromise of the issuer or attestation root
* malicious user approval or lack of user consent
* a compromised device relaying a valid challenge to another device
* false profile-event claims where no trusted internal eUICC callback exists
* weak subscriber onboarding performed by an MNO or identity provider

## 16. Formal Verification Targets

The first formal-verification scope should be protocol correctness, not only ML-DSA arithmetic.

### Required properties

```text
1. TBS serializer and parser are bijective.

2. The applet cannot sign a transcript whose verifier_id,
   nonce, request_id, suite_id, or policy_id differs from
   the validated request.

3. Hybrid acceptance requires both signatures over identical TBS bytes.

4. A consumed request_id cannot be accepted twice.

5. PROFILE_ACTION_OBSERVED cannot be reached through
   a host-exposed APDU path.

6. Evidence fragment reassembly produces exactly the original
   evidence bytes or fails closed.

7. Any malformed length, version, suite, or origin fails before signing.
```

This is where Assay fits naturally. The cryptographic primitive matters, but transcript construction, APDU fragmentation, policy binding, and downgrade resistance are where product-grade failures usually hide.

---

## 17. Deployment Boundaries

Q-SEAL v0.1 should target:

1. operator-managed IoT eUICCs
2. embedded secure elements under OEM control
3. private eUICC deployments with applet-management rights
4. regulated devices where carrier, OEM, and relying party cooperate

It should not begin as a consumer-app feature that assumes any third-party mobile application can install or freely call an eSIM applet.

The first commercial product is an issuer-integrated attestation service, not an SDK asking random consumer eSIMs to become HSMs on demand.

---

## 18. Product Statement

> Q-SEAL provides hybrid, quantum-resistant secure-element attestation for enrollment, credential lifecycle, and regulated device trust. It binds a verifier challenge, policy-defined action, and optional object digest to non-exportable classical and post-quantum keys held in the subscriber secure element.

For device-integrity use cases:

> Q-SEAL combines subscriber secure-element proof with OEM or TEE device evidence, allowing relying parties to verify that a recognised secure element and a verified device jointly participated in a single challenge-bound transaction.
